## 1. MVP 目标

MVP 用于验证一条完整产品链路：

> 用户用自然语言提出上海旅行需求，系统补全关键信息，生成一份经过时间和预算校验的结构化行程；用户在导游页面打开地图和浏览器定位，到达景点后获得讲解，并可围绕当前景点提问。

MVP 不追求全国覆盖、后台自动定位或真实订票，只验证以下核心命题：

1. AI 生成的行程能否被约束校验，而不是一篇不可执行的长文本。
2. 景点讲解能否关联当前地点、行程和历史偏好。
3. 当模型或定位能力不稳定时，用户是否仍有可用的手动路径。

## 2. 一个完整演示场景

用户在首页输入：

> 下周去上海玩两天，预算 3000 元，我想去外滩和上海博物馆，不吃辣，不想走太累，住得安静一点。

系统完成：

1. 提取目的地、天数、预算、必去景点、饮食、体力和住宿偏好。
2. 对缺失的日期或预算口径进行一次澄清。
3. 从上海景点库中召回候选 POI。
4. 生成两天结构化计划，包含景点、餐饮、交通、休息和费用。
5. 检查开放日、时间冲突、每日密度和预算。
6. 展示每日时间轴、推荐理由和事实来源。
7. 用户进入导游页面，允许浏览器定位。
8. 页面在前台检测到外滩附近后，弹出外滩讲解。
9. 用户询问“这里为什么重要？附近还能看什么？”
10. 系统结合当前景点、当天计划和用户“不想走太累”的偏好回答。

## 3. MVP 功能范围

### 3.1 规划会话

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| MVP-REQ-001 | 用户可以用一段自然语言输入旅行需求 | P0 |
| MVP-REQ-002 | 系统提取城市、天数、日期、预算、人数、必去景点和偏好 | P0 |
| MVP-REQ-003 | 仅对阻止规划的关键字段追问；允许通过表单补充 | P0 |
| MVP-REQ-004 | 用户可以标记“必去”和“不想去”的景点 | P0 |
| MVP-REQ-005 | 若用户需求冲突，展示原因并建议放松条件 | P0 |
| MVP-REQ-006 | 对话上下文可支持“第二天轻松一点”等修改指令 | P1 |

MVP 只支持：

- 上海。
- 1–3 天。
- 单人或两人出行。
- 中文。
- 人民币。
- 预算可按“总预算”或“每日预算”表达。

### 3.2 景点候选与检索

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| MVP-POI-001 | 展示符合城市和主题的候选景点 | P0 |
| MVP-POI-002 | 每个景点展示简介、建议时长、开放信息和所在区域 | P0 |
| MVP-POI-003 | 支持关键词召回和向量召回的简单融合 | P0 |
| MVP-POI-004 | 景点事实带有来源标签 | P0 |
| MVP-POI-005 | 未确认的实时信息标记为“出发前确认” | P0 |

MVP 数据库只建设约 30 个上海核心 POI，重点覆盖：

- 外滩。
- 上海博物馆。
- 豫园。
- 城隍庙。
- 南京路。
- 武康路。
- 思南公馆。
- 静安寺。
- 上海自然博物馆。
- 东方明珠或陆家嘴。
- 其他能够组成合理半日/一日路线的景点。

每个 POI 至少包含：

- POI ID、名称、别名和行政区。
- 经纬度。
- 景点类型和主题标签。
- 建议游玩时长。
- 开放日与开放时间。
- 票价或“价格未知”。
- 预约要求或“来源未确认”。
- 适合人群和体力强度。
- 讲解文本。
- 来源列表和更新时间。

### 3.3 结构化行程

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| MVP-PLAN-001 | 生成 1–3 天结构化行程，而不是只返回 Markdown | P0 |
| MVP-PLAN-002 | 每天包含景点、餐饮、交通、休息和时间范围 | P0 |
| MVP-PLAN-003 | 必去景点必须出现在计划中，除非用户同意移除 | P0 |
| MVP-PLAN-004 | 检查每日总时长、景点密度和预算 | P0 |
| MVP-PLAN-005 | 检查开放日和明显时间冲突 | P0 |
| MVP-PLAN-006 | 使用简化路线距离/时间估算安排顺序 | P0 |
| MVP-PLAN-007 | 每个核心事实绑定证据引用或“未知”标记 | P0 |
| MVP-PLAN-008 | 展示每日预算和行程总预算 | P0 |
| MVP-PLAN-009 | 支持重新生成一次，并保留上一版本 | P1 |
| MVP-PLAN-010 | 支持替换单个景点并显示影响 | P1 |

MVP 的行程校验规则：

- 景点开始时间不得早于当天可游玩时间。
- 景点不得安排在闭馆日或闭馆时段。
- 每个交通段必须保留基础移动时间。
- 每日活动时长不得超过用户允许范围。
- 必去景点缺失时必须显式报错。
- 总预算超过用户上限时不得标记为通过。
- 每天至少保留一个用餐窗口。
- “轻松”模式每天原则上不超过 2–3 个主要景点。

### 3.4 行程展示

行程页面至少包含：

- 行程概览。
- 总天数、总预算和步行强度。
- 每日时间轴。
- 景点卡片。
- 交通段。
- 餐饮和休息建议。
- 费用估算。
- 风险或待确认提示。
- 来源查看入口。
- 进入“现场导游”的按钮。

用户不应看到内部 Prompt、Agent 推理过程或完整向量检索结果；可以查看推荐依据和来源摘要。

### 3.5 Web 定位与现场导游

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| MVP-GUIDE-001 | 用户主动点击后请求浏览器定位权限 | P0 |
| MVP-GUIDE-002 | 在页面保持前台时检测附近计划内景点 | P0 |
| MVP-GUIDE-003 | 展示“疑似到达”“定位精度不足”或“未找到景点”等明确状态 | P0 |
| MVP-GUIDE-004 | 用户可以始终手动选择当前景点 | P0 |
| MVP-GUIDE-005 | 到达候选唯一时展示约 90 秒讲解 | P0 |
| MVP-GUIDE-006 | 讲解支持浏览器文字转语音，失败时保留文字 | P0 |
| MVP-GUIDE-007 | 用户可以围绕当前景点继续提问 | P0 |
| MVP-GUIDE-008 | 同一导游会话不连续重复弹出同一景点 | P0 |
| MVP-GUIDE-009 | 用户可点击“不是这里”纠正识别结果 | P0 |
| MVP-GUIDE-010 | 已访问讲解在弱网时可从浏览器缓存读取 | P1 |

浏览器定位限制必须在产品中明确展示：

- 只支持 HTTPS 或 localhost。
- 用户必须授权定位。
- 页面进入后台、浏览器关闭或系统挂起后，不保证继续识别景点。
- MVP 不申请后台定位，不开发 Android 原生应用。

建议初始开发参数：

- 定位精度小于 100 米才参与自动候选。
- POI 半径默认 150 米，可按景点配置。
- 连续两次或两次以上采样落在范围内才提示。
- 触发后 10 分钟内不重复提示同一景点。
- 所有阈值均可配置，不视为最终现场结论。

### 3.6 长期记忆与指代

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| MVP-MEM-001 | 保存用户明确表达的偏好 | P0 |
| MVP-MEM-002 | 保存上一版行程和其中的景点/酒店实体 | P0 |
| MVP-MEM-003 | 支持“上次那家酒店”的简单实体解析 | P0 |
| MVP-MEM-004 | 多个候选时展示确认，不自动猜测 | P0 |
| MVP-MEM-005 | 用户可查看并删除 MVP 记忆 | P0 |
| MVP-MEM-006 | 保存当前导游景点作为短期会话上下文 | P0 |

MVP 只实现以下指代场景：

1. “上次那家酒店” -> 历史行程中的住宿实体。
2. “昨天推荐的那个景点” -> 最近一次计划中的 POI。
3. “就这里” -> 当前导游会话景点。

MVP 不实现复杂跨城市、跨多年实体图谱，也不推断敏感个人属性。

### 3.7 缓存和降级

| 编号 | 需求 | 优先级 |
| --- | --- | --- |
| MVP-OPS-001 | LLM 或 RAG 失败时返回清晰的用户提示 | P0 |
| MVP-OPS-002 | 规划失败时提供一份上海静态模板行程 | P0 |
| MVP-OPS-003 | 模板行程仍可进入手动导游 | P0 |
| MVP-OPS-004 | 景点详情可进行短期缓存 | P1 |
| MVP-OPS-005 | 导游讲解生成超时后展示静态讲解 | P0 |

模板行程必须明确标记为“备用方案”，不能伪装成个性化实时生成结果。

## 4. MVP 不实现的功能

- Android、iOS 或其他原生客户端。
- 浏览器后台持续定位。
- 自动订票、支付、酒店预订。
- 全国多城市和千万级知识库。
- 真实景区拥堵、余票和临时闭馆数据。
- 完整的多 Agent 动态集群。
- 多人协作和投票。
- 多语言讲解。
- 完整离线地图导航。
- 复杂 Plan Patch 求解和任意条件重规划。
- 生产级账号、支付、营销和会员体系。
- 未经授权的公开网页大规模抓取。

## 5. 页面与交互

MVP 至少包含四个页面或同一 SPA 的四个页面状态：

### 5.1 首页/规划对话

- 旅行需求输入框。
- 示例问题快捷入口。
- Slot 澄清卡片。
- 生成进度。
- 错误和重试入口。

### 5.2 行程详情

- 行程摘要。
- 每日时间轴。
- 景点、交通和餐饮卡片。
- 预算。
- 风险提示。
- 来源入口。
- “开始导游”按钮。

### 5.3 现场导游

- 地图和当前位置。
- 定位状态。
- 计划内附近景点。
- 手动选择景点列表。
- 当前讲解。
- 播放/暂停语音。
- 追问输入框。
- “不是这里”按钮。

### 5.4 记忆

- 显式偏好列表。
- 历史行程列表。
- 用户可删除记忆。
- 记忆来源和更新时间。

## 6. MVP 技术实现

### 6.1 前端

| 项 | 方案 |
| --- | --- |
| 框架 | Vue 3 + TypeScript + Vite |
| 路由 | Vue Router |
| 状态 | Pinia |
| 地图 | 高德 JS API |
| 定位 | 浏览器 Geolocation API |
| 本地缓存 | IndexedDB |
| 语音 | 浏览器 Web Speech API，失败时纯文字 |
| 响应式 | 手机优先，兼容桌面浏览器 |

### 6.2 后端

| 项 | 方案 |
| --- | --- |
| 语言 | Java 21 |
| 框架 | Spring Boot 3 |
| AI | Spring AI |
| 数据 | MongoDB |
| 缓存 | Redis，用于 POI 详情和重复请求缓存 |
| RAG | 小规模文件向量索引 + 关键词过滤，预留 VectorStore 接口 |
| 路线 | 先使用直线距离系数/高德路线结果，后续替换 OR-Tools |
| 工具 | 一个最小 MCP 服务，暴露 `search_poi`、`get_poi_detail`、`get_weather_forecast` |
| 评测 | JUnit + 独立评测 CLI |

MVP 不引入 OpenSearch、Milvus、Kubernetes 和多服务集群。知识检索规模较小，优先保证链路正确和可解释，保留后续替换为混合检索的基础设施接口。

### 6.3 最小工作流

```text
IDLE
  -> COLLECTING
  -> READY
  -> RETRIEVING
  -> PLANNING
  -> VALIDATING
  -> DONE

任一步失败 -> NEEDS_CLARIFICATION 或 DEGRADED
```

系统只在以下三个位置调用 LLM：

1. 自然语言需求抽取。
2. 基于已校验结构化计划生成可读推荐文案。
3. 基于当前 POI 证据和上下文生成导游回答。

景点筛选、排程、预算和时间校验使用确定性代码。

### 6.4 最小数据集合

| 集合 | 用途 |
| --- | --- |
| `pois` | 30 个上海 POI |
| `poi_chunks` | 约 60–100 条来源化知识片段 |
| `trips` | MVP 行程 |
| `plan_versions` | 计划版本 |
| `conversations` | 规划对话 |
| `user_preferences` | 显式偏好 |
| `entity_references` | 历史行程和景点实体引用 |
| `guide_sessions` | 导游会话和触发记录 |
| `eval_runs` | 评测运行结果 |

## 7. API 范围

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| `POST` | `/api/planning/sessions` | 创建规划会话 |
| `POST` | `/api/planning/sessions/{id}/messages` | 提交自然语言需求 |
| `POST` | `/api/planning/sessions/{id}/generate` | 生成行程 |
| `GET` | `/api/trips/{tripId}` | 获取行程 |
| `GET` | `/api/trips/{tripId}/versions` | 获取历史版本 |
| `POST` | `/api/trips/{tripId}/regenerate` | 重新生成 |
| `POST` | `/api/guide/sessions` | 创建导游会话 |
| `POST` | `/api/guide/sessions/{id}/locate` | 提交浏览器坐标并匹配 POI |
| `POST` | `/api/guide/sessions/{id}/select-poi` | 手动选择景点 |
| `POST` | `/api/guide/sessions/{id}/ask` | 当前景点追问 |

规划生成接口使用普通请求即可；如生成时间超过 10 秒，增加 SSE 进度事件。

## 8. 评测集与 MVP 门槛

### 8.1 评测集

建立 30 条固定评测样本：

| 类型 | 数量 |
| --- | --- |
| 正常规划 | 8 |
| 预算/时间/开放冲突 | 4 |
| 代词与记忆 | 6 |
| 导游问答与证据 | 8 |
| 工具/模型失败降级 | 4 |

样本必须固化为可重复输入，禁止每次手工修改后声称指标提升。

### 8.2 MVP 完成门槛

以下为发布门槛，而非已经取得的结论：

1. 30 条评测可以一键运行并生成 JSON/Markdown 报告。
2. Plan IR Schema 合法率为 100%。
3. 已定义硬约束的校验通过率为 100%，不允许将冲突计划标记为通过。
4. 规划、导游和记忆核心用例成功率达到 90% 以上。
5. 核心静态事实至少有 90% 带来源引用。
6. 定位被拒绝、模型超时和检索失败时均有可用降级路径。
7. 从输入需求到展示行程的目标 P95 不超过 20 秒。
8. 从提交定位或手动选择景点到展示首段文字的目标 P95 不超过 3 秒。

如果浏览器定位在现场测试中不稳定，MVP 仍可通过手动选择景点完成验收；自动定位只作为增强能力，不作为唯一入口。

## 9. 端到端验收

### 9.1 规划验收

1. 输入本文档的示例需求。
2. 系统正确抽取上海、两天、3000 元、外滩、上海博物馆、不吃辣和轻松节奏。
3. 对缺失字段最多追问一次。
4. 生成两天结构化行程。
5. 外滩和上海博物馆出现在行程中。
6. 时间、预算和开放信息能够通过 Validator。
7. 页面显示预算、时间轴、餐饮、交通、来源和提示。

### 9.2 导游验收

1. 用户点击“开始导游”并授权浏览器定位。
2. 页面在前台检测当前位置。
3. 命中外滩附近时展示候选或讲解。
4. 拒绝定位时用户可以从列表选择外滩。
5. 显示文字讲解并允许播放语音。
6. 提问“附近还能看什么”时，回答只使用当前城市和证据内容。
7. 点击“不是这里”后可以重新选择景点。

### 9.3 记忆验收

1. 系统保存“上次住过某酒店”的历史行程实体。
2. 用户输入“上次那家酒店，这次换一家安静点的”。
3. 系统正确召回历史酒店实体。
4. 若存在两个候选，页面要求用户确认。
5. 用户可以在记忆页面删除该记录。

### 9.4 降级验收

1. 模拟模型调用超时，页面展示备用模板行程。
2. 模板行程明确标记为降级结果。
3. 模板行程仍允许进入手动导游。
4. 模拟 RAG 失败，导游回答不得编造景点事实。

## 10. 开发顺序

### Step 1：契约和骨架

- 创建 Spring Boot 后端和 Vue 3 前端。
- 定义 Plan IR、POI、Evidence、UserPreference 数据模型。
- 启动 MongoDB、Redis 和本地开发环境。

### Step 2：规划闭环

- 实现需求抽取。
- 导入 30 个 POI。
- 实现候选检索。
- 实现基础排程和 Validator。
- 实现行程页面。

### Step 3：导游闭环

- 实现高德地图和浏览器定位。
- 实现距离匹配、手动选择和讲解。
- 接入浏览器 TTS 与追问。

### Step 4：记忆和评测

- 实现历史实体和指代确认。
- 实现 30 条评测样本。
- 实现超时、检索失败和模板降级。
- 输出可复现的 MVP 评测报告。

## 11. 需要先确认的产品决策

以下决策会影响实现细节：

1. 首发示范城市是否固定为上海。
2. 前端是否接受 Vue 3 + TypeScript。
3. MVP 是否必须接入真实大模型，还是允许无 API Key 时只运行模板闭环。
4. 是否已有高德开放平台 Web 端 Key。

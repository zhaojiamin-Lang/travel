## 1. 文档目的

本文档定义旅行导游助手的产品范围、核心流程、技术架构、数据模型、验收指标和迭代计划，作为后续设计、开发、测试和上线验收的共同依据。

项目不以“堆叠更多 Agent 框架”为目标，而以三个结果为核心：

1. 用户只需用自然语言表达偏好，就能得到时间、预算、交通和开放条件可验证的行程。
2. 用户在景区现场可以获得与当前位置、当前行程和停留时长匹配的讲解。
3. 每个推荐和事实可追溯；模型、工具或网络异常时，系统能够降级并恢复到可用状态。

## 2. 产品定义

### 2.1 产品目标

旅行导游助手提供两类连续服务：

- **行前规划**：用户选择目的地和想去的景点，Agent 补全出行要素，生成多日可执行行程。
- **行中导游**：用户到达景点后自动或手动唤起讲解，并可围绕当前景点提问、调整后续安排。

### 2.2 目标用户

| 用户类型 | 核心诉求 |
| --- | --- |
| 自由行用户 | 不想手工查攻略，希望快速生成符合预算和节奏的路线 |
| 亲子/家庭游客 | 需要儿童友好、低强度、餐饮和休息安排 |
| 文化深度游客 | 需要有来源、有上下文、可追问的景点讲解 |
| 多人同行群体 | 需要共同选点、比较方案、实时调整 |
| 老年或无障碍用户 | 需要低步行强度、清晰路线、文字和语音双通道 |

### 2.3 MVP 使用假设

以下为当前开发基线，后续可以通过产品决策调整：

- 首发地区为中国大陆，默认中文、人民币和北京时间。
- 首发客户端为响应式 Web/PWA，不开发 Android 原生应用。
- 首发采用单城市试点，默认上海；最终试点城市以 POI、讲解资料和交通数据质量决定。
- 地图与 POI 基础能力优先接入高德开放平台。
- 后端采用 Spring Boot 3 和 Spring AI；MVP 使用模块化单体，MCP、评测和数据管道保留独立部署能力。
- 门票余量、景区拥堵、实时开放状态只有在取得合法、稳定的数据源后才展示为确定事实。

### 2.4 非目标

MVP 不包含以下能力：

- 自动完成支付、出票或不可撤销的预订。
- 承诺全国所有景点的实时开放、票价和拥挤度准确。
- 自动生成未经授权的历史、文化或版权内容。
- 在浏览器关闭、Tab 挂起或系统限制后台定位时承诺自动触发讲解。
- 使用全自动 Agent 替代确定性时间、预算和路线校验。

## 3. 产品核心场景

### 3.1 场景 A：从自然语言生成行程

用户输入：

> 下个月去上海玩三天，我想去外滩和上海博物馆，预算 4000 元，不吃辣，不想每天走太久，住得安静一点。

系统应完成：

1. 提取目的地、日期、天数、预算、必去景点、饮食、住宿和步行强度。
2. 只追问影响行程正确性的必要信息，例如出发日期、同行人数或预算是否包含交通。
3. 检索候选景点、餐饮和住宿区域。
4. 根据开放时间、预约要求、交通耗时和用户偏好生成行程。
5. 完成时间、预算、动线和体验校验。
6. 展示每日安排、推荐理由、证据和可替换项。

### 3.2 场景 B：现场自动讲解

用户打开导游页面并到达外滩附近，Web/PWA 在前台检查位置并识别景点后：

1. Web/PWA 客户端请求浏览器定位并识别当前可能景点及置信度。
2. 若候选唯一且满足触发条件，自动唤起当前景点导游卡。
3. 系统生成“当前、下一步、约 90 秒”的短讲解，并支持继续深入。
4. 页面保持前台时继续更新位置；定位失败或页面被挂起时允许手动选择景点。

### 3.3 场景 C：自然语言指代

用户输入：

> 上次那家酒店不错，这次换一家同样安静但便宜一点的。

系统应识别“上次那家酒店”对应的历史住宿实体，并区分：

- 已明确的事实：上次入住的酒店。
- 用户偏好：安静。
- 新的软约束：更便宜。
- 缺失信息：本次目的地、日期和预算。

存在多个候选实体时，系统应展示候选并要求确认，不能自行猜测。

### 3.4 场景 D：行程中重规划

用户迟到或景区临时关闭时，系统应计算最小变更方案，例如：

- 替换一个景点。
- 缩短某一站停留时间。
- 调整顺序。
- 取消低优先级景点。
- 保持原有方案但提示延迟。

每次调整生成新的行程版本，用户可查看差异并回滚。

- 已明确的出行日期和时间范围。

- 预算上限。

- 景点偏好和主题。
- 路线顺滑度。
- 每日景点数量和节奏。
- 餐饮类型和住宿风格。

地理围栏建议采用可配置的多信号评分：

```text
触发分数 =
  POI 地理匹配
  + GPS 精度奖励
  + 稳定停留时间奖励
  + 当前行程匹配奖励
  + 运动方向/路线匹配奖励
  - 邻近高密度 POI 歧义惩罚
```

初始默认值仅用于开发验证：定位精度小于 100 米、围栏内停留 15–30 秒、触发后冷却 10 分钟。实际阈值必须通过不同景点现场测试调整，不能作为全国统一固定值。

## 5. 核心业务规则

### 5.1 事实可信度

事实优先级建议为：

1. 官方景区、交通或政府数据。
2. 有合同或正式授权的一手数据。
3. 高德等地图服务的结构化字段。
4. 可信 OTA 或百科内容。
5. 用户评论和社区内容。
6. 模型推断。

模型推断不能作为开放时间、票价、预约要求等确定性事实的唯一依据。

### 5.2 时间与预算

- 所有时间统一保存时区，MVP 默认 `Asia/Shanghai`。
- 行程时间包括游玩、交通、排队、用餐和休息，不得只计算景点停留。
- 预算必须记录口径、币种和估算区间。
- 若票价或交通价格为估算值，应明确标记“预计”。
- 无可行计划时，系统必须返回冲突原因和可选择的放松条件。

### 5.3 动态数据缺失

以下字段无法获得可靠实时数据时：

- 开放状态：提示出发前向官方确认。
- 门票余量：不得显示“有票”，改为跳转官方入口或提示未知。
- 拥挤度：不得生成确定性“无需排队”结论。
- 天气：保留预报时间，禁止伪装为实时观测。

### 5.4 讲解内容

- 讲解区分事实、传说、观点和模型推断。
- 历史事实需要来源；无法溯源的故事不得描述为确定历史。
- 默认短讲解控制在约 90 秒可读完/听完的长度。
- 用户可以随时说“讲详细一点”“只讲下一步怎么走”。
- 安全和紧急信息优先于普通讲解，但不能替代官方应急指引。

```text
  +-- Orchestrator / Workflow State Machine    |
  +-- Requirement & Slot Service               |
  +-- Plan Compiler & Constraint Solver        |
  +-- Guide Service                            |
  +-- Memory Service                           |
  +-- Evaluation / Trace Gateway               |
  |                                             |
  +-- Spring AI Model Gateway                  |
  +-- RAG Pipeline                             |
  +-- MCP Client                               |
  |                                             |
  +-- MCP Tools --------------------------------+
        |          |          |
     POI/Route   Weather    Trip/Memory
        |          |          |
     MongoDB    Redis    OpenSearch
```

MVP 推荐模块化单体，按领域拆包；只有当 MCP 工具或检索服务出现独立扩缩容需求时再拆分微服务。不要为了“看起来像微服务”提前拆散事务边界。

### 6.2 推荐技术栈

| 层 | 技术 |
| --- | --- |
| Web/PWA | TypeScript、Vue 3、Vite、IndexedDB、Service Worker、浏览器 Geolocation |
| 后端 | Java 21、Spring Boot 3、Spring AI、Spring Security、Bean Validation |
| Agent 状态 | 自研持久化状态机或 Spring Statemachine |
| 业务数据 | MongoDB |
| 缓存/限流 | Redis |
| 知识检索 | OpenSearch，支持 BM25 + Vector + 过滤 |
| 路线求解 | OR-Tools CP-SAT / Routing |
| 地图 | 高德 JS API + Web Service API |
| 可观测性 | OpenTelemetry、结构化日志、指标和 Trace |
| 评测 | 离线评测 CLI + 自动化测试 + CI Gate |
| 部署 | Docker Compose 用于开发；生产按实际环境容器化部署 |

Spring AI 的模型调用应通过统一 Gateway 封装，避免业务代码同时绑定多个厂商 SDK。模型、Embedding、Rerank 和 TTS 都应支持配置切换。

### 6.3 Agent 职责边界

| 角色 | 职责 | 不负责 |
| --- | --- | --- |
| Supervisor | 识别任务、选择步骤、检查终止条件 | 直接决定预算和时间冲突 |
| Requirement Worker | 提取 Slot、识别冲突和缺失项 | 生成最终行程 |
| Research Worker | Query 改写、检索和多源证据整理 | 编造实时信息 |
| Plan Compiler | 将需求转换为 Plan IR | 自由生成无结构长文本 |
| Constraint Solver | 时间、交通、预算和路线求解 | 生成导游叙事 |
| Critic / Validator | 规则校验、缺陷报告和体验评审 | 替代确定性求解器 |
| Guide Worker | 当前景点讲解和上下文问答 | 修改行程而不经用户确认 |
| Memory Worker | 偏好抽取、实体解析和记忆治理 | 无依据地推断敏感属性 |

## 8. RAG 技术方案

### 8.1 知识源

建议优先接入：

- 官方景区和文旅部门公开资料。
- 有授权的地图 POI 数据。
- 城市公共交通和轨道交通数据。
- 有授权的餐饮、酒店和门票数据。
- 经人工审核的城市文化资料。

MVP 不建议直接追求“千万级文档”。第一阶段优先建设 500–1000 个高质量 POI 和足够覆盖评测题目的 Chunk，再按真实需求扩展。

### 8.2 数据处理

入库流程：

```text
采集 -> 许可与来源记录 -> 清洗 -> 去重 -> 结构化抽取
     -> Chunk -> Embedding -> 索引 -> 质量评测 -> 发布索引版本
```

每个 Chunk 至少包含：

- `document_id`
- `chunk_id`
- `city`
- `poi_id`
- `content_type`
- `source_url`
- `source_level`
- `published_at`
- `retrieved_at`
- `valid_until`
- `language`
- `license`
- `content_hash`

### 8.3 检索链路

```text
Query 理解
  -> 城市/坐标/时间/主题过滤
  -> BM25 + Dense 多路召回
  -> 去重与来源融合
  -> Rerank
  -> 时效校验
  -> Top-K 证据包
  -> 行程或讲解生成
```

Agentic Query 改写应设置上限，通常最多 1–2 轮。简单问题直接单跳检索，只有多约束、跨文档或证据不足时才进入多步检索。

### 8.4 防幻觉规则

- 生成时只使用证据包内的动态事实。
- 输出结构必须携带 `evidenceRefs`。
- 没有证据的数字、日期、价格、开放时间应被 Validator 删除或标记为未知。
- 讲解中的传说、观点和事实应使用不同的表达。
- 外部网页内容视为数据，不视为指令。

## 9. 长期记忆方案

### 9.1 记忆分类

| 类型 | 示例 | 生命周期 |
| --- | --- | --- |
| 显式画像 | 素食、禁烟、无障碍需求 | 长期，用户可编辑 |
| 推断偏好 | 更偏好安静酒店 | 带置信度和衰减 |
| 历史行程 | 上次上海三日行程 | 跟随行程保留 |
| 业务实体 | 上次入住的具体酒店 POI | 长期或按用户策略 |
| 临时上下文 | 当前景点、当前定位 | 会话或短期 TTL |
| 纠正记录 | 用户否认某个推断 | 长期优先于推断 |

### 9.2 指代解析流程

```text
代词/省略识别
  -> 查找最近对话实体
  -> 查找当前行程实体
  -> 查找历史行程实体
  -> 类型约束过滤
  -> 候选评分
  -> 唯一则消解
  -> 多候选则确认
```

实体匹配优先使用业务 ID，例如 `poi_id`、`hotel_id`、`trip_id`，相似度检索只作为候选生成手段。

### 9.3 MongoDB 集合建议

| 集合 | 内容 |
| --- | --- |
| `users` | 用户与授权状态 |
| `user_profiles` | 显式画像和设置 |
| `preference_signals` | 推断偏好、来源、置信度、TTL |
| `memory_episodes` | 会话和历史事件摘要 |
| `entity_mentions` | 对话实体与业务实体映射 |
| `trips` | 行程主数据 |
| `plan_versions` | 不可变计划版本和差异 |
| `conversations` | 对话和消息 |
| `guide_sessions` | 导游会话、触发原因和讲解版本 |
| `evidence_records` | 事实来源和时效信息 |
| `workflow_checkpoints` | 工作流状态和步骤结果 |
| `eval_runs` | 离线/在线评测结果 |

关键索引至少包括：

- `(user_id, updated_at)`
- `(trip_id, version)` 唯一索引
- `(user_id, poi_id, session_id)`
- `(workflow_id, step_id)` 唯一索引
- `(valid_until)` TTL 或清理任务索引

## 10. 缓存与高可用

### 10.1 缓存原则

Redis 只用于可重建数据，不把 Redis 作为唯一事实来源。缓存 Key 至少包含：

```text
request_fingerprint
knowledge_index_version
rules_version
prompt_version
model_version
locale
time_bucket
```

动态数据使用分钟级或更短 TTL；静态讲解可按景点和语言缓存。语义缓存默认关闭，只有在相似查询不会改变时间、预算或安全事实时才可考虑。

### 10.2 降级策略

| 级别 | 策略 | 用户提示 |
| --- | --- | --- |
| L1 | 完整 Agentic RAG + 约束求解 + 动态工具 | 正常个性化规划 |
| L2 | 静态知识 + 模板行程 + 用户约束调整 | 说明部分信息为模板或历史数据 |
| L3 | 本地静态行程、离线讲解和手动攻略 | 明确离线模式 |

LLM 不可用时，不应把旧缓存结果伪装成刚刚生成的实时结果。

### 10.3 工具稳定性

- 单次 MCP 工具调用有独立超时。
- 只读工具允许有限次指数退避重试。
- 写工具必须使用幂等键，默认不自动重试。
- 单步骤和整条 Workflow 都设置最大轮次与最大耗时。
- 熔断器打开时直接进入降级路径。
- 所有失败写入 Trace，并进入评测样本池。

## 11. 评测流水线

### 11.1 三阶段评测

| 阶段 | 检查内容 | 推荐实现 |
| --- | --- | --- |
| 预处理 | 开放时间、日期、季节、交通可达性、坐标 | 代码规则 + 动态工具 |
| 合规性 | 总预算、每日时长、餐饮住宿、预约要求 | 确定性断言 + CP-SAT |
| 体验性 | 折返、拥挤、休息不足、节奏和解释质量 | 可计算评分 + LLM Judge |

评测输出结构化缺陷报告：

```json
{
  "code": "TIME_CONFLICT",
  "severity": "ERROR",
  "day": 2,
  "itemIds": ["item_08", "item_09"],
  "message": "交通时间不足",
  "suggestedAction": "EXTEND_TRANSIT_OR_MOVE_ITEM"
}
```

最多允许两轮自动修复。仍失败时，向用户解释冲突并请求放宽约束。

### 11.2 数据集

MVP 建立不少于 300 条分层评测任务，后续扩展到多城市：

- 单人、情侣、亲子、老人、多人同行。
- 不同天数、预算和步行强度。
- 必去、排除、预约和临时关闭。
- 代词指代、记忆纠正和歧义确认。
- 弱网、工具超时、模型失败和错误定位。
- 中英文或方言表达。

数据分为开发集、测试集和不参与调参的 Holdout 集。每次 Prompt、模型、知识索引、检索规则或 Solver 变化都运行回归。

### 11.3 指标定义

| 指标 | 定义 |
| --- | --- |
| 计划 Schema 合法率 | 通过 Plan IR JSON Schema 的计划占比 |
| 硬约束满足率 | 无时间、预算、开放或必去冲突的计划占比 |
| 时间冲突 Precision/Recall/F1 | 与人工标注冲突对比 |
| Unsupported Claim Rate | 没有有效证据的原子事实占比 |
| RAG Recall@10 | Top-10 是否包含标注证据 |
| nDCG@10 | 检索排序质量 |
| P50/P95 规划延迟 | 从请求到可展示计划 |
| 首次讲解延迟 | 从触发到首段文字/音频可用的时间 |
| 工具成功率 | 工具返回有效 Schema 的比例 |
| 降级率 | 进入 L2/L3 的请求占比 |
| 恢复成功率 | 断点恢复后完成任务的占比 |
| 缓存有效率 | 命中缓存且数据仍满足时效要求的比例 |
| 每次行程成本 | Token、Embedding、Rerank 和 TTS 成本合计 |
| 围栏召回率 | 现场应触发场景中成功触发的比例 |
| 围栏误触发率 | 不应触发场景中错误触发的比例 |

### 11.4 CI 门槛

任何 P0 合规回归直接阻断合并。建议门槛：

- Plan IR Schema 合法率：100%。
- 确定性硬约束校验通过率：100%。
- P0 评测集无新增未解释失败。
- RAG Recall@10、Unsupported Claim Rate 等核心指标不得相对基线下降超过 2 个百分点。
- 平均单次行程成本不得超出预算阈值。
- 涉及工具调用、Prompt、模型和索引版本的改动必须附带评测报告。

## 12. Web/PWA 与定位方案

### 12.1 客户端组件

- 地图：高德 JS API。
- 定位：浏览器 Geolocation API，只能由用户主动授权。
- 本地存储：IndexedDB，用于行程、缓存讲解和触发事件。
- Web 缓存：Service Worker 用于应用壳和已访问内容缓存。
- 连续位置更新：导游页面保持前台时使用 `watchPosition`；页面隐藏后不承诺持续定位。
- 到达识别：前端采集位置，后端或前端按距离、精度和会话状态评分。

### 12.2 缓存讲解内容

每个缓存记录建议包含：

- 景点 ID、名称、坐标和围栏。
- 文本讲解和引用摘要。
- 附近路线和下一站信息。
- 版本号、下载时间和过期时间。
- 来源引用和内容完整性校验值。

Web MVP 只承诺应用壳和已访问内容的弱网可用，不承诺浏览器关闭后的后台服务。

### 12.3 触发与防抖

触发状态至少包括：

```text
IDLE -> CANDIDATE_FOUND -> DWELLING -> TRIGGERED -> COOLDOWN
```

必须满足：

- 定位精度满足当前围栏配置。
- 用户已主动开启导游模式且页面正在前台。
- 连续采样不是单点噪声。
- 处于合理距离或 POI 多边形范围内。
- 在示范版中允许通过“确认当前景点”完成人工兜底。
- 当前会话未触发过该景点。
- 用户未关闭自动讲解。

用户点“不是这里”后，系统应记录误判，并在当前会话内不再自动提示该 POI。

## 14. 非功能需求

### 14.1 性能目标

以下为 MVP 目标门槛，需要通过实际测试回填结果：

- 普通必填字段抽取 P95 小于 3 秒。
- 完整三日行程生成 P95 小于 20 秒；流式展示首个进度事件小于 2 秒。
- 已缓存且无动态变化的计划查询 P95 小于 500 毫秒。
- 导游触发后首段文字 P95 小于 3 秒。
- 离线导游包打开 P95 小于 1 秒。

### 14.2 稳定性

- 核心 API 月可用性目标 99.5% 以上。
- MCP 工具超时为 5–10 秒，具体按工具配置。
- 最大 Agent 轮次按任务配置，禁止无限循环。
- 所有外部调用必须有超时、总预算和降级路径。
- 服务重启后 Workflow 可从最后 Checkpoint 恢复。

### 14.3 安全与隐私

- 所有服务间调用使用身份认证。
- MCP 工具使用最小权限 Scope。
- 日志默认脱敏手机号、Token、精确位置和用户原文。
- 位置数据按用途最小化收集，并支持删除。
- Prompt、工具结果和外部网页均视为不可信输入。
- 防止 SSRF、路径穿越、任意 URL 抓取和工具参数注入。
- 高风险写操作执行前要求人工确认。
- 审计日志不可由普通业务用户修改。

### 14.4 可访问性

- 支持文字字号调整、语音播放和暂停。
- 讲解文本与音频内容保持等价。
- 支持老人、儿童和低步行强度方案。
- 重要提示不能只用颜色表达。

### 14.5 可观测性

每次请求生成唯一 `trace_id`，并贯通：

- API 入口。
- Slot 抽取。
- 检索与重排。
- 模型调用。
- MCP 工具。
- 约束求解。
- 校验与修复。
- 计划发布和导游触发。

Trace 记录版本信息但不记录无必要的敏感原文。开发环境支持按 `trace_id` 回放任务。

## 15. MVP 数据规模

MVP 不承诺虚构的“千万级”数据规模，建议先达到：

- 单试点城市 500–1000 个高质量 POI。
- 主要 POI 均有基础介绍、开放信息和来源记录。
- 重点景点有 30 秒、90 秒和深入版讲解文本。
- 至少 100 个景点具备可离线使用的讲解包。
- 不少于 300 条评测任务。
- 至少一个动态开放/天气工具的可靠接入。

数据量和指标达到真实测试条件后，再扩展城市或知识规模。

## 16. 迭代计划

### Phase 0：工程骨架

- 建立后端、Web/PWA、文档和本地开发环境。
- 定义 Plan IR Schema、错误码和模块边界。
- 接入 MongoDB、Redis、OpenSearch、模型 Gateway 和 Trace。
- 建立最小 CI。

验收：能够保存一条会话、一次模型调用和一条结构化计划草稿。

### Phase 1：结构化行程闭环

- 自然语言 Slot Filling。
- 用户选择和排除 POI。
- 检索候选 POI。
- 交通矩阵与 CP-SAT 排程。
- 预算、时间和开放条件 Validator。
- 计划展示、版本和单点替换。

验收：单城市可生成并验证三日行程，时间冲突可被确定性检出。

### Phase 2：RAG 与记忆

- 知识采集、清洗、索引和引用。
- 混合召回、重排和 Query 改写。
- 动态事实工具和时效仲裁。
- Mongo 记忆集合、实体映射和指代消解。
- 第一批评测集。

验收：推荐和讲解可追溯到来源；明确支持“上次那家酒店”等表达。

### Phase 3：Web/PWA 导游

- 行程展示与现场 Today Card。
- 手动定点、前台到达识别和候选匹配。
- 讲解文本、TTS 和上下文问答。
- 已访问讲解缓存和弱网展示。
- 定位失败、弱网和误触发反馈。

验收：在试点城市保持页面前台时能够识别到达景点，手动导游路径始终可用。

### Phase 4：重规划、评测和稳定性

- 天气、闭馆和延迟事件。
- Plan Patch、版本差异和回滚。
- CI 评测流水线、Holdout 集和回归报告。
- Workflow Checkpoint、熔断和多级降级。
- 成本、延迟和 SLO 仪表盘。

验收：完成端到端 Demo，所有核心指标有可复现实测数据。

### Phase 5：产品增强

- 多人协作和投票。
- 更完善的 PWA 离线能力。
- 合法接入订票、余票或酒店价格。
- 多语言讲解。
- 自动旅行日记，默认由用户主动开启。

## 18. 端到端验收条件

以下条件全部满足后，MVP 才视为完成：

1. 用户能用一段自然语言完成单城市三日行程规划。
2. 行程可展示必去地点、预算、时间、交通、餐饮和休息安排。
3. 明确的时间冲突和预算越界无法绕过 Validator。
4. 至少 90% 的核心事实可以追溯到来源记录，且未知实时信息不会被写成确定事实。
5. “上次那家酒店”至少支持从历史行程解析；歧义时能请求确认。
6. Web/PWA 在页面前台且已授权定位时支持到达景点提示，也支持手动景点触发。
7. 拒绝定位或弱网时仍能使用手动导游和已缓存讲解。
8. 模型或工具故障时可自动进入降级路径，并明确告知用户。
9. Workflow 在指定中断场景下可从 Checkpoint 恢复。
10. CI 能在 Prompt、模型、知识索引或 Solver 发生回归时阻断发布。
11. 所有上线指标有日期、评测集版本和环境信息，不使用无法复现的数字。

## 19. 风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| 多 Agent 链路不稳定 | 重复调用、不可控成本 | 确定性步骤代码化，限制轮次和状态 |
| 动态旅游数据缺失 | 实时信息不可信 | 数据源分级、时效标记、明确不确定 |
| GPS 漂移和高密度 POI | 误触发讲解 | 多信号评分、停留时间、滞回、手动纠正 |
| 浏览器后台定位限制 | 页面关闭或挂起后无法自动触发 | 只承诺前台导游，提供手动选择与缓存兜底 |
| 记忆误推断 | 个性化结果错误 | 置信度、来源、TTL、用户纠正和删除 |
| 外部内容提示词注入 | 工具越权 | 内容隔离、Allowlist、权限和人工确认 |
| 评测过拟合 | 指标好看但体验差 | Dev/Test/Holdout 分离，保留人工抽检 |
| 成本失控 | 无法长期运行 | Token 预算、缓存、分层模型、成本 Gate |
| 数据版权或内容错误 | 合规和信任风险 | 许可记录、来源审计、人工审核 |

## 20. 待确认决策

开发启动前需要确认，但不阻塞文档基线：

1. 首发城市是上海、北京还是其他城市。
2. 目标浏览器和最低兼容版本。
3. 是否首发即要求登录，还是长期保留游客模式。
4. 是否允许使用外部地图导航跳转，还是客户端内导航。
5. 是否已有合法的餐饮、酒店、门票或实时客流数据源。
6. 模型、Embedding、Rerank 和 TTS 的首选供应商及预算。
7. 是否需要公网部署，还是先完成本地可演示版本。

## 21. 简历亮点输出原则

项目完成后，简历只写入与代码、日志或评测报告一致的数字。建议保留以下五条能力线：

1. 结构化行程编译与约束求解。
2. Agentic RAG、事实时效仲裁和字段级证据。
3. MCP 工具层、持久化 Workflow Harness 和故障恢复。
4. MongoDB 长期记忆和实体指代消解。
5. 自动化评测、Trace 回放和 Web/PWA 前台导游。

没有真实评测记录时，应写“实现了什么”和“如何验证”，不写“提升 34%”“召回率 92%”等无法解释来源的数字。

## 1. 审计结论

当前版本已经完成一条可运行的演示链路：

```text
自然语言输入
→ 本地规则提取旅行要素
→ 补全缺失字段
→ 查询预置上海 POI
→ 规则生成结构化行程
→ 校验时间、预算、必去景点和关闭时间
→ Web 地图示意与行程展示
→ 手动选点或浏览器定位
→ 景点讲解、浏览器语音和上下文问答
```

但当前版本仍属于“可演示 MVP”，不是生产级旅行 Agent 平台。主要缺口包括：

- 自然语言理解目前主要是正则和关键词规则，尚未真正通过 LLM 完成多轮 Slot Filling。
- 路线时间为固定估算，没有接入真实高德路线矩阵。
- 高德地图需要配置 Key，目前验收时使用的是示意图。
- 行程只有单版本，重新生成、单点替换、版本比较和回滚尚未实现。
- 没有正式账号、跨设备历史行程、个人收藏和多人协作。
- 没有长期记忆、RAG、MCP、多 Agent、Harness 和自动评测平台。

## 3. P0：补齐当前 MVP 的产品与工程基础

### P0-01 使用 Spring AI 完成真正的结构化需求抽取

当前问题：

- 目的地、天数、预算和景点主要依赖正则匹配。
- “下周末”“玩个三四天”“预算别太高”等表达支持不足。
- 缺少字段的追问逻辑较固定。

需要实现：

- 使用 Spring AI `ChatClient` 完成意图识别和 Slot 抽取。
- 使用 JSON Schema 约束输出字段。
- 通过 Bean Validation 校验天数、预算、日期和人数。
- 对模型输出执行一次自动修复，修复失败后进入表单补全。
- 支持多轮对话修改，例如“预算改成 3500”“第二天别去博物馆”。
- 记录 Prompt 版本、模型版本和抽取结果。

所需技术：

- Spring AI `ChatClient`
- Structured Output / JSON Schema
- Jackson
- Jakarta Validation
- 服务端会话状态
- Prompt 版本管理

工程亮点：

- LLM 只负责语义理解，预算和时间仍由确定性代码校验。
- 支持自然语言与结构化表单两种入口共享同一份需求模型。
- 可形成“LLM Structured Output + 业务 Schema 双校验”的可靠性亮点。

### P0-02 接入真实高德路线与坐标服务

当前问题：

- 行程中的交通时间固定为 15/24 分钟。
- 未接入高德距离矩阵。
- POI 坐标是演示数据，尚未批量校验。
- 地图没有 Key 时只展示示意图。

需要实现：

- 使用高德 Web Service API 获取步行、公共交通和驾车路线。
- 使用距离矩阵计算多个 POI 之间的真实耗时。
- 统一处理 GCJ-02 坐标系。
- POI 选择时展示真实地图、地点详情和路线预览。
- API 失败时明确显示“估算时间”，不能伪装成实时路线。
- 导航可以跳转高德官方地图。

所需技术：

- 高德 JS API
- 高德 Web Service API：地理编码、POI 搜索、路径规划、距离矩阵
- 坐标转换
- 服务端限流与缓存
- 响应超时和降级

工程亮点：

- “真实路线时间矩阵 + 行程约束校验”，比单纯让 LLM 排景点更有可信度。
- 可以把“模型生成的行程”变成真正可执行的时间表。

### P0-03 建立正式的数据库迁移体系

当前状态：

- 使用 Hibernate `ddl-auto=update`。
- 还没有 Flyway 迁移脚本。
- H2 和 PostgreSQL 的数据类型兼容性需要进一步验证。

需要实现：

- 使用 Flyway 管理表结构。
- 为 PostgreSQL 建立正式 Schema。
- 将 Plan IR 存储为 PostgreSQL `JSONB`。
- 增加唯一约束、外键和必要索引。
- 增加测试用 H2 或 Testcontainers PostgreSQL。
- 写出数据备份和恢复步骤。

所需技术：

- Flyway
- PostgreSQL 16
- JSONB
- Spring Data JPA
- Testcontainers

工程亮点：

- 数据库结构可版本化、可回滚、可自动验证。
- 从“能运行”提升到“可部署、可升级”。

### P0-04 行程版本、重新生成和单点替换

当前问题：

- 每次生成只有版本 1。
- 没有修改行程的接口。
- 没有版本差异和回滚。

需要实现：

- 每次生成、替换、重规划都创建不可变版本。
- 支持“换掉这个景点”。
- 支持“第二天轻松一点”。
- 展示替换前后的时间、预算和路线变化。
- 支持回滚到上一版本。
- 使用乐观锁防止并发覆盖。

所需技术：

- Plan Version 数据模型
- PostgreSQL 事务
- JPA Optimistic Locking
- JSON Diff
- 规则化 Plan Patch

工程亮点：

- 行程有完整版本记录，可解释为什么发生调整。
- 这是后续实时重规划的基础。

### P0-05 完善会话和账号

当前问题：

- 使用 LocalStorage 中的匿名会话标识。
- 没有正式用户身份和跨设备同步。
- 对话记录没有保存在服务端。

需要实现：

- 登录或免登录游客身份。
- 游客升级为正式账号时迁移行程。
- 会话 Cookie 使用 HttpOnly、Secure 和 SameSite。
- 会话过期、删除和注销。
- 当前规划对话与导游对话持久化。
- 支持查看历史行程。

所需技术：

- Spring Security
- Cookie Session 或 JWT + Refresh Token
- BCrypt / Argon2
- PostgreSQL 会话表
- 可选 OAuth2 / 微信登录

工程亮点：

- 会话安全边界清晰。
- 用户数据可跨设备恢复，为长期记忆打下身份基础。

### P0-06 完善景点检索与选择

当前问题：

- `/api/pois` 目前返回全部 POI。
- 没有分页、关键词、区域、主题和票务过滤。
- 没有“排除景点”和候选池编辑。

需要实现：

- 按关键词、区域、主题、游玩时长和价格检索。
- 支持必去、想去、排除三类标记。
- 支持候选池数量限制和偏好排序。
- 用户选择的结果回写到规划需求。
- 增加空结果、重复名称和别名处理。

所需技术：

- Spring Data JPA Specification
- PostgreSQL 索引
- 可选 PostgreSQL Full Text
- 前端虚拟列表或分页

工程亮点：

- 用户可以真正参与旅行规划，而不是只接收系统结果。
- 候选池与硬约束分离，后续可以平滑接入向量召回。

### P0-07 实时事实与来源展示

当前问题：

- 开放时间和票价使用演示资料。
- 没有实时开放状态和天气。
- 所有来源都标记为 `DEMO`。

需要实现：

- 每个动态事实记录来源、抓取时间、有效期和可信度。
- 接入合法天气数据。
- 有可靠数据源时接入临时闭馆、余票和票价。
- 没数据时明确显示“待确认”。
- 前端支持字段级来源查看。

所需技术：

- 高德天气或合规第三方天气 API
- 景区官方数据或授权 OTA API
- Redis 短 TTL 缓存
- 数据源分级和时效仲裁

工程亮点：

- 解决旅行 AI 最关键的“信息过期”问题。
- 可形成字段级可信度和来源审计能力。

### P0-08 前端可用性与可访问性

当前页面已经具有响应式设计，但还需补齐：

- 键盘完整操作。
- 色弱、对比度和焦点态检查。
- 图片加载失败占位。
- 地图失败后的可访问替代内容。
- 更多手机尺寸和横屏测试。
- 语音播放失败和自动播放策略提示。
- 加载骨架、空状态和错误重试。

所需技术：

- WAI-ARIA
- Playwright 响应式截图测试
- Lighthouse
- axe-core
- Web Speech API

工程亮点：

- 不只“看起来漂亮”，还具备真实可用的交互质量。

## 5. P2：简历级高阶能力

### P2-01 Supervisor-Worker 多 Agent + 多轮 Slot Filling

当前未实现：

- 多 Agent 协作。
- 状态图。
- 模型驱动的追问策略。
- 任务级终止控制。

需要实现：

| Agent | 职责 |
| --- | --- |
| `SupervisorAgent` | 规划、导游、记忆和追问意图路由，控制终止 |
| `RequirementAgent` | Slot 抽取、缺失字段追问、需求修改 |
| `DiscoveryAgent` | POI、餐饮、住宿、天气和多源检索 |
| `ItineraryAgent` | 候选方案组织、调用路线和约束工具 |
| `CriticAgent` | 校验结果解释和一次修复 |
| `GuideAgent` | 现场讲解和当前景点问答 |
| `MemoryAgent` | 长期偏好和实体指代 |

需要明确，路线、预算和时间校验仍是确定性工具，不包装成 Agent。

所需技术：

- Spring AI
- Tool Calling
- 自定义 StateGraph 或 Spring Statemachine
- 持久化 Workflow State
- 最大轮次限制
- Agent 评测数据集

工程亮点：

-  Supervisor 控制固定状态机，而不是让多个 Agent 自由聊天。
- 每个 Agent 有输入输出 Schema、工具权限和终止条件。
- 可量化多轮 Slot Filling 完成率和平均追问轮次。

### P2-06 Redis 热点缓存与三级降级

当前未实现：

- 热门行程缓存。
- 语义缓存。
- LLM 异常 L2 模板降级。
- 服务故障 L3 静态兜底。

需要实现：

- 缓存 Key 包含需求指纹、数据版本、Prompt 版本和时区。

- 基础设施异常时返回本地静态方案。
- 用户能识别结果是实时、模板还是离线。

所需技术：

- Redis
- Resilience4j
- 数据版本
- 模板配置中心
- 前端降级标识

工程亮点：

- 高可用不仅是“缓存一下”，还要保证结果不误导用户。
- 可以量化缓存命中率、降级率和成本节省。

### P2-07 多阶段自动评测流水线

当前只有少量 JUnit 集成测试，没有完整评测平台。

需要实现：

| 阶段 | 检查 |
| --- | --- |
| 预处理 | 开放时间、季节、交通可达性、坐标 |
| 合规 | 预算、每日密度、必去景点、时间冲突 |
| 体验 | 折返、休息、拥挤、节奏和解释质量 |

需要建设：

- 开发集、测试集、Holdout 集。
- 规划、导游、记忆和故障注入样本。
- 确定性规则断言。
- LLM-as-Judge 只评价主观体验。
- CI 回归门禁。
- 指标版本和失败样本归档。

所需技术：

- JUnit 5
- Playwright
- Testcontainers
- LLM Evaluation Harness
- GitHub Actions 或其他 CI
- JSON/Markdown 报告

工程亮点：

- 证明“加 Agent 后没有把原来能用的功能弄坏”。
- 能定位指标下降来自 Prompt、检索、模型、工具还是排程。

### P2-08 全链路可观测性与 Trace 回放

当前未实现：

- 跨 Service 的 Trace。
- Prompt、检索和工具版本关联。
- 失败请求回放。

需要实现：

- 每次请求生成 `trace_id`。
- 记录模型、Prompt、知识索引、工具和规则版本。
- 记录耗时、Token、费用和失败原因。
- 只保存脱敏必要数据。
- 支持从 Trace 重放一次任务。

所需技术：

- OpenTelemetry
- Micrometer
- Grafana Tempo / Jaeger
- Prometheus
- Loki

工程亮点：

- Agent 系统从“看最终答案”升级为“可定位每一步为什么错”。
- 可做成本和质量的持续优化。

## 6. P2：建议新增的两条差异化亮点

### 亮点 A：结构化行程编译与约束修复

业务价值：

- 用户说“第二天轻松点”时，系统只调整必要的景点和时间。
- 用户迟到、天气变化或景点关闭时，快速生成可执行替代方案。

所需技术：

- Plan IR
- OR-Tools CP-SAT / Routing
- 时间窗口和交通矩阵
- Plan Diff / Patch
- 版本化

简历表达方向：

> 设计结构化行程编译与约束修复链路，将自然语言需求编译为时间、预算、交通和开放条件约束；基于最小差异 Patch 支持行程中重规划和版本回滚。

### 亮点 B：字段级证据与数据时效仲裁

业务价值：

- 区分“官方信息”“第三方信息”和“模型推断”。
- 对过期门票、开放时间或闭馆信息给出明确不确定性。

所需技术：

- Evidence Ledger
- 来源等级
- 有效期限
- 字段级引用
- 冲突仲裁
- 数据版本索引

简历表达方向：

> 构建字段级证据记录与时效仲裁机制，动态事实按来源权威性和有效期融合，使每条行程事实可追溯、可降级、可审计。

## 8. 推荐实施顺序

### 阶段 1：让当前 MVP 可信

1. Spring AI 结构化需求抽取。
2. 高德路线矩阵。
3. Flyway 与 PostgreSQL 正式 Schema。
4. 行程版本和单点替换。

### 阶段 2：让现场导游可靠

1. RequirementAgent。

## 9. 下一阶段验收建议

优先选择 P0-01、P0-02、P0-04 三项，因为它们直接决定行程是否真实可信：

- 用户复杂表达能否正确抽取。
- 路线时间能否真实计算。
- 行程能否安全修改和回滚。

建议下一阶段目标：

1. 100 条自然语言需求抽取测试，字段准确率可复现。
2. 上海主要 POI 全部通过真实高德路线接入。
3. 每次生成、修改、回滚均产生不可变版本。
4. 规划 P95 时延和模型成本可在接口中观测。
5. 所有动态事实明确显示来源与更新时间。

完成以上四项后，再进入 RAG、MCP 和多 Agent，项目会比较扎实。
